# Meme Vault Agent Guide

本文件定义所有代码代理在 Meme Vault 仓库中工作时必须遵守的长期规则。

当前任务消息中的明确要求优先于本文件。若任务要求与本文件冲突，应指出冲突并优先执行用户当前任务，不得自行扩大范围或猜测未说明的目标。

## 1. 开始工作前

修改代码前，必须先阅读：

1. `docs/CODEBASE_STATUS.md`
2. `docs/PROJECT_PLAN.md`
3. 与当前任务直接相关的 Model、Schema、Repository、Service、API、前端模块和测试
4. 若任务涉及 Luna 离线标签整理，再阅读 `docs/LUNA_TAGGING_WORKFLOW.md`

判断依据：

- 以实际代码和 `docs/CODEBASE_STATUS.md` 为当前实现依据。
- 以 `docs/PROJECT_PLAN.md` 为长期路线和阶段范围依据。
- 以 `README.md` 为用户可见的安装、启动、配置和功能说明。
- 不得仅根据旧提示词、文件名、历史版本或模型猜测当前实现。

开始修改前，先简要说明：

- 本次目标
- 当前调用链
- 预计修改的文件
- 明确不处理的内容
- 验证方法

## 2. 项目定位与技术栈

Meme Vault 是一个个人 Meme 收藏、管理、检索和创作网站。

主要技术栈：

- 后端：Python、FastAPI、SQLAlchemy、SQLite、Pydantic、Pillow、Pytest
- 前端：Vite、原生 TypeScript、HTML、CSS、Vitest、jsdom
- 图片：本地文件系统保存原图、缩略图和模板参考图
- 数据：SQLite 保存业务元数据，不保存图片二进制
- AI：通过可配置 Provider 支持图片分析、图像向量和后续语义功能

除非任务明确要求，否则不得引入 React、Vue、Next.js 或新的大型框架。

## 3. 分层约束

后端保持以下职责分离：

```text
API Route
  -> Service
  -> Repository / Storage / AI Client
  -> Database / File System / External Provider
```

必须遵守：

- API Route 只处理 HTTP 输入、依赖、状态码和错误转换。
- Service 负责业务编排、事务边界和跨组件协调。
- Repository 负责数据库查询、写入和 `flush`。
- Storage 负责图片保存、读取、缩略图和清理。
- AI 模块负责 Provider 协议、请求构造、响应解析和模型能力。
- Schema 负责外部输入输出验证。
- Model 负责 ORM 关系和数据库约束。

不得：

- 在 API Route 中直接执行数据库查询。
- 在 Repository 中编排文件和外部 API。
- 在前端直接访问数据库或本地图片目录。
- 为绕过现有接口而复制一套平行业务逻辑。
- 在多个位置重复实现同一种规范化、事务或清理规则。

新增功能前，优先寻找现有 Service、Repository、Schema、测试模式和错误转换并复用。

## 4. 开发原则

### 小步修改

一次任务只完成用户指定的阶段。

不要顺手实现下一版本功能，不要把局部任务扩张成大规模重构。

若发现无关问题：

- 在最终报告中记录。
- 除非它会阻止当前任务，否则不要同时修改。

### 最小影响

- 只修改完成任务所必需的文件。
- 保持现有公开 API 和前端行为兼容，除非任务明确要求破坏性变化。
- 不因个人偏好重命名大量文件、类、函数或字段。
- 不为了“未来可能需要”创建空目录、空接口或过度抽象。
- 优先选择容易理解、容易测试的直接实现。

### 先理解再修改

修改已有流程前，必须先追踪完整调用链。

涉及数据写入时，检查：

- 事务边界
- rollback 行为
- 文件清理
- 外键约束
- 重复提交
- 部分失败
- 历史数据兼容

涉及异步前端请求时，检查：

- 加载状态
- 错误状态
- 重复点击
- 过期响应
- 页面或 Meme 切换
- 未保存状态

## 5. 数据与文件安全

以下文件和目录属于本地运行数据，不得提交：

- `data/meme_vault.db`
- `data/.ai_settings.key`
- `data/images/`
- `data/thumbnails/`
- `data/template_images/`
- `data/tagging_work/`
- 数据库备份
- `.env`
- API Key 或访问令牌
- 用户真实 Meme 图片和分析结果

不得：

- 输出或记录完整 API Key。
- 把密钥写入源码、测试快照、日志或文档。
- 删除、覆盖或迁移真实数据库，除非用户明确要求。
- 对真实数据库运行批量写入脚本，除非用户明确要求。
- 为测试连接真实外部 AI Provider。
- 在测试中依赖用户本地数据。

测试必须使用临时数据库、临时目录和伪造的外部服务。

涉及数据库维护脚本时：

- 默认只读或 dry-run。
- 写入必须要求显式的 `--apply`。
- 应用前必须备份数据库。
- 必须记录可审计的变更结果。
- 不得删除来源为 `user` 或 `manual` 的标签，除非用户明确批准。

## 6. AI 与 Provider 规则

Qwen Chat、视觉分析、图像 Embedding 和其他协议是不同能力，不得因为模型来自同一厂商而强行共用协议。

新增或修改 AI Provider 时，必须分别确认：

- Provider 协议
- 模型能力类型
- 请求 payload
- 图片编码方式
- 响应结构
- 超时和重试
- 错误映射
- 模型是否可被设置为对应用途

不得：

- 把纯文本模型设置为视觉分析模型。
- 把 Chat Completions 协议用于专用图像向量接口，除非厂商文档明确支持。
- 假设 Codex 中可用的 Luna 额度能够自动被 Meme Vault 后端复用。
- 为使用 Codex 订阅额度而向应用写入伪造的 Base URL、API Key 或模型记录。

`gpt-5.6-luna` 也可以作为 OpenAI API 模型使用，但这与 Codex 中的模型额度是两条独立路径。只有用户明确提供 OpenAI API 凭据、确认接受 API 计费，并要求在线接入时，才允许把它配置为 Meme Vault 的在线视觉模型。

AI 建议默认不能直接修改 Meme。描述、标签、标题和模板匹配必须经过现有确认流程，或通过任务明确指定的安全离线导入流程。

测试外部 AI 功能时优先使用 fake client、mock transport 或固定响应。

只有用户明确要求在线验证，并且环境已配置安全凭据时，才允许请求真实 Provider。

## 7. Meme 与图片组规则

一个 Meme 可以包含一张或多张图片。

必须保持：

- 图片按零基 `position` 升序排列。
- 最小 `position` 的图片是封面。
- 完整图片组分析必须按 `position` 顺序读取。
- 添加、删除或排序图片后必须保持 `position` 连续。
- 删除最后一张图片应被拒绝。
- 文件操作与数据库操作必须正确处理部分失败。
- 删除 Meme 时必须处理图片、缩略图、关系、Caption 和关联数据。

不得只检查封面便假设完整图片组有效。

## 8. 标签规则

标签处理应优先复用已有标签。

默认要求：

- 使用简体中文标签。
- 固定外语梗名、角色名或外语表达更准确时可以保留外语。
- 避免同义重复、大小写重复和无信息量标签。
- 避免“图片”“表情包”“搞笑”等过度宽泛标签，除非它们具有实际筛选价值。
- 单次 AI 建议遵守现有数量限制。
- 用户手动标签优先于 AI 或离线整理标签。
- 标签规范化逻辑应集中实现，不要散落在多个入口。
- 离线标签整理只能先生成候选，不得默认直接写入正式数据库。

## 9. Luna 离线标签整理

当任务包含以下目标时，必须启用本节并阅读 `docs/LUNA_TAGGING_WORKFLOW.md`：

- 使用 Luna 给 Meme 打标签
- 批量补标签
- 标签清洗、合并、归一化
- 检查错标、漏标或低信息标签
- 离线整理 Meme 元数据

### Luna 的角色

Luna 只负责视觉理解和候选生成，不负责数据库决策。

默认分工：

- 主代理或协调代理：准备批次、分配范围、检查输出、运行验证、汇总报告。
- Luna 工作代理：按图片顺序查看完整 Meme，生成严格结构化的标签候选。
- 本地校验器：验证格式、Meme ID、标签数量、来源保护和词典约束。
- 导入器：默认 dry-run，只有用户明确要求后才允许 `--apply`。

### 强制边界

Luna 执行标签任务时：

- 不调用 Meme Vault 中配置的 Qwen、OpenAI、DeepSeek 或其他外部 Provider。
- 不修改 Provider、模型或 API Key 设置。
- 不直接修改 SQLite。
- 不运行 `--apply`。
- 不删除 `user` 或 `manual` 来源标签。
- 不修改标题、描述、模板、关系或文案，除非当前任务明确要求。
- 不自行创建大量新标签。
- 不把猜测当作事实。
- 无法判断时输出低置信度或标记人工复核，不强行贴标签。

### 批次规则

- 默认每批 8 至 12 个 Meme。
- 长图、聊天截图、文字密集图或多图 Meme 每批 4 至 6 个。
- 同一个 Meme 只能由一个 Luna 工作代理处理。
- 多个 Luna 可以并行处理互不重叠的批次。
- 每个工作代理只读取当前批次所需文件，避免反复加载完整仓库。
- 每个批次完成后结束该工作上下文，避免长期累积无关上下文。

### 输出规则

Luna 默认只写入当前批次的 `candidates.jsonl`。

每条候选至少包含：

- `meme_id`
- `add_tags`
- `remove_tags`
- `confidence`
- `reason`
- `needs_review`

完成后必须运行候选校验器。

若校验失败：

- 只修复当前批次候选。
- 不绕过校验。
- 不降低校验规则来迁就错误输出。

## 10. 前端规则

前端使用原生 TypeScript。

必须：

- 保持严格类型，避免无必要的 `any`。
- 网络请求集中在 API 客户端。
- 共享接口放在类型模块。
- DOM 渲染、状态编排和业务控制器保持现有职责边界。
- 修改交互时同步处理成功、加载、空状态和错误状态。
- 对竞态风险使用请求中止、代次或现有项目模式。
- 保持键盘操作、按钮禁用和基本可访问性。

不得：

- 直接在多个组件中重复 fetch 逻辑。
- 用整页刷新掩盖状态同步问题。
- 为局部功能引入新的前端框架。
- 使用 `innerHTML` 拼接未可信输入。
- 删除已有错误反馈或未保存提醒。

## 11. 数据库变更

修改 ORM 模型或持久化结构前，必须检查当前 SQLite 兼容策略和现有启动迁移方式。

数据库升级必须：

- 兼容已有数据库。
- 可重复运行。
- 避免重复回填。
- 保持外键有效。
- 为新增行为编写旧数据升级测试。
- 不依赖删除用户数据库后重新创建。

不得以“删除数据库重新启动”作为正式迁移方案。

## 12. 测试要求

修改后运行与变更范围直接相关的测试。

完成阶段前，原则上运行完整验证：

```powershell
npm.cmd --prefix frontend run typecheck
npm.cmd --prefix frontend test
npm.cmd --prefix frontend run build
python -m pytest -v
```

若只修改后端，可先运行相关 Pytest，再运行完整 Pytest。

若只修改前端，可先运行相关 Vitest，再运行 typecheck、完整前端测试和 build。

若修改以下内容，必须补充或更新测试：

- API 行为
- Service 事务
- Repository 查询
- 数据库升级
- 图片文件清理
- AI payload 或响应解析
- 前端状态变化
- 错误映射
- 批量任务和 dry-run/apply 行为

不得为了通过测试而删除、跳过或弱化已有断言。

若某项验证无法运行，最终报告必须说明：

- 未运行的命令
- 具体原因
- 已完成的替代验证
- 剩余风险

不得把未运行的测试描述为通过。

## 13. 文档规则

行为、启动方式、配置、API 或数据结构发生变化时，更新相应文档。

职责：

- `docs/CODEBASE_STATUS.md`：记录已经落地的当前实现。
- `docs/PROJECT_PLAN.md`：记录长期路线和阶段完成情况。
- `docs/LUNA_TAGGING_WORKFLOW.md`：记录 Luna 离线标签任务的执行协议。
- `README.md`：记录面向使用者的安装、启动、配置和主要功能。
- `AGENTS.md`：只记录长期代理规则，不记录一次性任务进度。

不要在多个文档复制大段相同内容。

只有实际实现并通过相应验证后，才把计划项标记为完成。

## 14. Git 规则

开始前检查工作区状态。

必须保留用户已有的未提交修改。

不得：

- 使用 `git reset --hard`。
- 使用 `git clean -fd`。
- 强制推送。
- 擅自 rebase。
- 修改或覆盖与当前任务无关的用户改动。
- 因测试失败而回退用户原有代码。
- 提交真实数据库、密钥、构建缓存或本地图片。

除非用户明确要求，否则不要创建分支、提交 commit、打 tag 或 push。

若用户要求提交：

- 只提交本次任务相关文件。
- 使用清晰的提交信息。
- 提交前检查 `git diff` 和 `git status`。
- 不把无关修改混入提交。

## 15. 子代理与并行工作

可以使用子代理处理互不重叠的只读探索、测试分析、独立实现或标签批次。

使用子代理时：

- 给每个子代理明确、互斥的任务范围。
- 告知它需要阅读本文件及相关项目文档。
- 避免多个代理同时修改同一文件。
- 标签任务按不重叠的 Meme ID 或批次划分。
- 主代理负责整合、检查冲突和最终验证。
- 子代理的结论不能代替实际代码检查和测试。
- 不因可以并行而扩大任务范围。

小型、集中任务优先由单个代理完成，避免额外上下文和协调成本。

## 16. 完成标准

只有满足以下条件时，任务才算完成：

- 指定功能已经实现。
- 修改符合现有分层。
- 相关测试已添加或更新。
- 要求的验证已经运行。
- 文档与实际实现一致。
- 未泄露密钥或修改真实用户数据。
- 没有把无关重构混入任务。
- 最终 diff 已检查。

最终报告应包含：

1. 实现摘要
2. 修改文件及职责
3. 实际调用链或数据流
4. 测试命令与结果
5. 未完成内容或风险
6. 三个值得用户理解的关键实现点

完成用户指定阶段后停止。不要自行继续开发下一阶段。
