# Meme Vault v2.2 开发任务书
## Publisher Bridge：通用发布适配器与内容创作工作台

**当前版本：** v2.1  
**目标版本：** v2.2.0  
**项目：** Meme Vault / 暗苟，夏，Meme  
**优先级：** P0  
**开发原则：** 核心平台无关、Publisher 插件化、本地优先、控制复杂度。

---

## 一、项目目标

Meme Vault 已经具有 Meme 管理、搜索、收藏和文案等能力。

v2.2 需要向「内容创作与跨平台分发」扩展，建立统一的 Publisher Bridge。

以后用户应能：

1. 在 Meme Vault 内选择一批 Meme。
2. 为每张 Meme 独立编写图下文案。
3. 调整图片与文案的顺序，保存完整帖文。
4. 在 Meme Vault 内预览最终图文结构。
5. 选择目标平台，将内容交给对应 Publisher 插件。
6. 由插件完成平台特定的排版、上传、草稿创建或发布操作。
7. 查看发布结果、错误及历史记录。

**v2.2 只负责 Meme Vault 内部的完整创作流程与通用适配协议，不要求实现任何真实第三方平台的发布功能。**

未来的小黑盒、B站等 Publisher 分别作为独立插件开发。

## 二、开发前置要求

首先检查当前 v2.1 的实际代码，确认：

- FastAPI API / Service / Repository 分层。
- 前端应用入口、导航与现有编辑器组件。
- Meme 和 MemeImage 的存储及读取方式。
- Caption Lab 的数据结构。
- Collection 与现有导出任务机制。
- SQLite 建表与迁移方案。
- Visitor / Admin 权限边界。
- 已有测试和前端设计规范。

优先复用已有基础设施，不重复造数据库、任务队列和认证系统。

不得直接照搬旧版代码结构。如果 v2.1 已经调整架构，以当前实际实现为准。

## 三、P0：帖文创作工作台

新增独立的 Publisher Workspace。

### 3.1 帖文草稿

支持：

- 创建、编辑、删除、复制帖文。
- 设置帖文标题。
- 保存正文开头和末尾的可选文本。
- 从图库添加 Meme。
- 为每张图片编辑独立图下文案。
- 图片和文案整体拖动排序。
- 删除、替换图片。
- 草稿自动保存与恢复。
- 帖文列表、最近编辑时间、发布历史入口。
- 保存后重新打开继续创作。

首要使用场景为「约 25 张 Meme + 25 条对应文案」的合集。

不把 25 张硬编码成上限。合理支持更长的合集，由 Publisher 插件报告各平台限制。

### 3.2 图库集成

在现有 Library / Search / Collection 中提供轻量的「添加到帖文」入口。

要求：

- 支持单选和批量添加。
- 支持选择新建帖文或现有草稿。
- 添加完成后可以继续浏览图库。
- 在编辑器内也能调用已有搜索能力选图。
- 不破坏原有卡片交互、收藏管理及浏览体验。

### 3.3 文案设计

每个帖文条目由图片引用和对应文案组成。

特别注意：

**帖子图下文案不等于 Meme 自身的 Description，也不等于 Caption Lab 的全局文案。**

同一 Meme 可以出现在不同帖子中，拥有完全不同的文案。

后续可以提供从 Caption Lab 复制现有文案的能力，但复制后必须独立编辑，不能建立会造成联动修改的共享关系。

### 3.4 预览

提供平台无关的通用图文预览：

图片 01  
文案 01

图片 02  
文案 02

……

要求与编辑结果保持一致，允许空文案，保留换行。

预览不应假装已经完整模拟小黑盒等平台的真实编辑器。

平台专属预览由未来的插件能力决定。

## 四、P0：统一帖文数据模型

创建独立的 PostDraft / PostItem 领域模型。

建议字段：

**PostDraft**

- id
- title
- intro_text
- outro_text
- status
- created_at
- updated_at
- revision

**PostItem**

- id
- post_id
- meme_id
- meme_image_id
- position
- caption

其中 `meme_image_id` 表示实际选择发布的图片，兼容 Meme Vault 已有的多图 Meme 结构。

允许同一图片在不同帖子中使用，必要时也允许同一帖子中重复使用。

图片通过 ID 引用现有资料库资源，不为每个帖子复制原图。

图片缺失、原 Meme 被删除或文件不可读取时，帖子应保持可打开、可修复，不能静默丢失整篇草稿。

数据库修改必须兼容现有用户数据，不能破坏旧表。

## 五、P0：Publisher Bridge 插件协议

这是 v2.2 的核心。

Meme Vault 内部只认识统一 Publisher 接口，不包含小黑盒、B站等平台的业务代码。

### 5.1 插件注册

建立轻量插件注册机制。

每个 Publisher 提供标准 Manifest，声明：

- plugin_id
- name
- version
- protocol_version
- supported_content_types
- capabilities
- limits
- execution_mode

Capabilities 可包含：

- 图文内容
- 多图内容
- GIF 支持
- 创建远端草稿
- 直接发布
- 返回发布链接
- 排版预览
- Dry Run

插件自行声明支持能力，不允许 Meme Vault 假设所有平台都有完整功能。

未实现的能力必须明确返回 unsupported。

### 5.2 通用发布包

Meme Vault 负责把草稿转换为标准 PublishPackage。

包内至少包含：

- 协议版本
- 帖文 ID 与版本
- 标题
- 正文文本
- 有序内容条目
- 每张图片的本地资源
- 对应的图下文案
- MIME 类型及必要文件元数据
- 本次请求的唯一 ID

推荐采用 JSON Manifest + Assets 的形式。

需要支持将内容导出成独立目录或 ZIP，以方便不同语言实现的 Publisher 读取。

**平台专属 Markdown、HTML、编辑器 JSON 和上传协议不应成为 Meme Vault 的核心数据格式。**

这些转换属于 Publisher 插件的职责。

### 5.3 插件执行边界

v2.2 先支持两种工作模式：

**A. 标准发布包导出**

Meme Vault 生成 PublishPackage，交给外部程序使用。

无需任何真实平台插件也能工作。

**B. 本地 Publisher 调用**

通过明确注册和管理员配置的受信任本地插件，传入标准发布包，等待结构化执行结果。

优先使用跨语言友好的进程调用和 JSON 数据交换方式。

禁止直接执行来自帖子内容的任意命令；不使用 `shell=True`；执行入口必须在可信配置中明确指定。

暂不建设完整插件商店、在线安装中心或复杂依赖管理系统。

为以后扩展 HTTP / 远程 Publisher 保留协议空间即可。

### 5.4 插件返回结构

统一定义执行结果：

- attempt_id
- plugin_id
- status
- external_post_id（可选）
- external_url（可选）
- error_code（可选）
- error_message（可选）
- started_at / finished_at

需要区分以下状态：

- prepared：已完成本地内容准备
- remote_draft：远端草稿已创建
- published：平台确认已发布
- failed：执行失败

不得将「准备完成」「已交付插件」冒充「平台发布成功」。

### 5.5 任务与重试

- 每次执行保存独立 Attempt 记录。
- 发布任务需要能够查询状态。
- 操作期间不得使编辑器长时间无响应。
- 失败后保留原始草稿与错误详情。
- 记录输入草稿版本和幂等标识。
- 重试必须由用户明确触发。
- 对已经发布成功或状态不确定的任务，不得盲目重复发布。
- 插件超时、崩溃或返回非法数据时，应正确记录失败或未知状态。

参考现有任务管理基础设施，采用最简单可靠的实现。

## 六、P1：Publisher 管理界面

在现有管理界面中增加 Publisher 入口。

展示：

- 已注册插件。
- 名称、版本与能力。
- 启用状态。
- 当前可用性。
- 最近执行结果。

在帖文编辑器中，根据插件能力显示可选的发布目标。

未安装任何真实 Publisher 时，仍允许正常编辑帖文、预览和导出发布包。

不需要开发插件商店。

## 七、P0：Mock Publisher 与黑盒测试

必须实现一个无外部依赖的 Mock Publisher。

它不连接小黑盒，不访问互联网，也不使用真实账号。

需要支持：

1. 读取标准发布包。
2. 校验 JSON 和图片资源。
3. 按顺序解析所有内容条目。
4. 模拟成功。
5. 模拟超时和失败。
6. 返回标准执行结果。
7. 生成供开发者核对的本地输出。

Mock Publisher 应当作为真实独立插件运行，不能仅在 Meme Vault 内部写死假返回值。

通过它证明：

**未来接入新平台只需开发插件，不需要修改 Meme Vault 的核心业务逻辑。**

## 八、权限与安全

- 帖文管理、发布包导出和插件调用仅允许 Admin。
- Visitor 不得查看私人草稿或触发 Publisher。
- 不把平台登录 Cookie、Token 或密码写入帖文。
- 真实平台凭据由对应插件独立负责。
- 不把本地绝对路径暴露到公共前端接口。
- 发布包中的文件路径必须进行规范化与安全检查。
- 防止目录穿越及不受信任的命令执行。
- 限制插件执行时间和必要资源消耗。
- 临时文件可控清理，避免长期堆积。
- 日志不得泄漏敏感认证信息。

保留 Meme Vault 的本地优先原则。

## 九、非目标

v2.2 暂时不做：

- 小黑盒真实发帖。
- 小黑盒逆向 API 接入。
- B站等其他平台真实发布。
- 自动维护平台登录态。
- 定时发布。
- AI 自动生成整篇帖子。
- 多账号运营。
- 云端插件市场。
- 自动跨平台同步评论、点赞与数据统计。
- 大规模重构现有前端或后端。

这些功能以后通过独立 Publisher 或新版本逐步增加。

**不要为了未来可能存在的需求提前实现复杂框架。**

## 十、测试与验收

### 10.1 创作流程

- 可以创建一个包含 25 张图片的帖子。
- 每张图片都有独立文案。
- 图片拖动后文案正确跟随。
- 可以重复引用同一 Meme。
- 可以使用多图 Meme 中指定的图片。
- 自动保存后刷新页面不丢失内容。
- 后端重启后草稿仍可恢复。
- 同一张 Meme 在两篇帖文中的文案互不影响。
- 缺失图片会明确提示且可以修复。
- 编辑器不会明显破坏现有图库交互。

### 10.2 桥接流程

- 能成功生成包含 25 张图片的 PublishPackage。
- 图片、文案与顺序完全正确。
- Mock Publisher 可以读取并执行。
- 能模拟成功、失败和超时。
- 能正确显示执行状态。
- 未安装 Mock 之外的平台插件时系统仍正常工作。
- 插件损坏不能导致整个 Meme Vault 无法启动。
- 禁止插件调用时不影响草稿编辑及导出。

### 10.3 工程质量

- 后端 Pytest 通过。
- 前端 Vitest 通过。
- TypeScript typecheck 通过。
- Production Build 通过。
- 原有 API 和关键功能回归测试通过。
- 数据库迁移经过旧数据兼容验证。
- 不留下明显的并发保存、重复触发与状态错乱问题。

## 十一、建议开发顺序

**Phase A：基础模型**

核对 v2.1，完成 PostDraft / PostItem 数据模型、Repository、Service 与 API。

**Phase B：前端编辑器**

完成帖文管理、图库选图、图片排序、逐图文案、自动保存和预览。

**Phase C：Bridge 协议**

完成标准发布包、插件 Manifest、注册机制和派发接口。

**Phase D：Mock Publisher**

实现独立测试插件，跑通整个发布包交付及结果回传流程。

**Phase E：测试与收尾**

检查权限、迁移、错误恢复、前后端测试与用户交互，并更新必要文档。

## 十二、交付要求

交付时提供：

1. v2.2 功能实现。
2. 通用 Publisher 插件协议文档。
3. 独立 Mock Publisher。
4. 完整的自动化测试。
5. 一份简短的开发与验收总结。
6. 后续小黑盒 Publisher 的最小对接示例。

文档尽量收敛，不创建大量重复的过程性 Markdown。

建议将稳定的插件协议说明集中存放在 `docs/publisher-plugin-api.md`。

### 最终完成标准

管理员可以在 Meme Vault 内创建包含约 25 张 Meme 的完整帖文，为每张图填写独立文案，保存、修改、预览，然后通过统一 Publisher Bridge 把内容完整交付给独立 Mock Publisher，获得正确的执行状态。

整个过程无需访问任何外部平台。

以后接入小黑盒 Publisher 时，**不需要修改帖子数据模型、编辑器主体或 Bridge 核心协议，只需新增符合协议的插件和必要的通用兼容处理。**

至此，Meme Vault v2.2.0 开发完成。
